# 13. ANTI-PATTERN / "ANTI-AI-SLOP" MODEL

Lucien must not implement a subjective:

```text
"looks AI-generated" = bad
```

rule.

`ANTI_PATTERN_LIFECYCLE.md` must define evidence-backed anti-patterns.

An anti-pattern record must explain:

- observed recurring structure;
- why it becomes harmful;
- contexts where the criticism applies;
- contexts where it may be legitimate;
- usability/accessibility/performance/maintainability consequences;
- supporting sources;
- counterexamples;
- confidence;
- acceptance state.

Examples of future candidate concepts MAY include:

```text
DECORATIVE_CARD_OVERLOAD
FAKE_DASHBOARD_DENSITY
WEAK_INFORMATION_HIERARCHY
CONTAINER_NESTING_WITHOUT_SEMANTIC_PURPOSE
MEANINGLESS_METRIC_CARDS

EXCESSIVE_PILL_CONTROLS
UNJUSTIFIED_GLASS_EFFECTS
GENERIC_MARKETING_HERO_STRUCTURE
MOTION_WITHOUT_INTERACTION_VALUE
ICON_DECORATION_WITHOUT_SEMANTIC_VALUE
```

These names are examples only.

W01 MUST NOT mark them ACCEPTED merely because they appear in this handoff.

Their job is to demonstrate the kind of evidence Lucien should later be capable of collecting.

# 15. PATTERN PROMOTION LAW

```text
RAW SOURCE
→ OBSERVATION
→ CROSS-SOURCE COMPARISON
→ CANDIDATE
→ MAINTAINER REVIEW
→ ACCEPTED / REJECTED
→ DEPRECATED when superseded
```

Promotion should consider:

- quality of sources;
- number of independent sources;
- agreement/disagreement;
- context similarity;
- counterexamples;
- target applicability;
- accessibility impact;
- performance impact;
- maintainability impact.

No arbitrary numeric score may masquerade as objective truth unless the scoring model itself is accepted.

# 16. CONTRADICTION HANDLING

Lucien must preserve disagreement.

Example:

```text
Source A:
always place destructive actions behind confirmation.

Source B:
allow immediate delete with undo for low-risk reversible entities.
```

Correct result:

```text
CONTEXTUAL TRADEOFF
```

not:

```text
majority wins
```

Knowledge records must support counterexamples and non-applicability.

# 20. ACQUISITION PROTOCOL

`KNOWLEDGE_ACQUISITION.md` must define an explicit run lifecycle.

## K0 — Request

Resolve:

- acquisition goal;
- requested domain;
- target audience/workflow;
- whether the run is broad research or target-specific;
- authority requesting it.

## K1 — Source discovery

Find candidate sources.

Do not extract conclusions yet.

## K2 — Source qualification

For each source:

- classify source type;
- classify authority weight;
- verify identity;
- capture version/date/SHA where available;
- capture license/provenance state.

## K3 — Observation extraction

Extract bounded observations.

Do not convert them into standards.

## K4 — Comparison

Cluster observations by domain/problem/context.

Preserve contradictions.

## K5 — Candidate synthesis

Produce:

- pattern candidates;
- anti-pattern candidates;
- vocabulary/terminology discoveries;
- unresolved questions.

## K6 — Review packet

Return candidate knowledge to Maintainer.

No self-promotion.

## K7 — Promotion

Only after Maintainer acceptance:

- mark accepted records;
- record acceptance authority;
- update reusable worker guidance.

# 21. SOURCE EVALUATION PROTOCOL

`SOURCE_EVALUATION.md` must require source-specific questions.

Examples:

For standards/specifications:

- normative or explanatory?
- current version?
- official owner?
- implementation implications?

For open-source repositories:

- exact commit/tag?
- active maintenance?
- representative source path?
- real tests?
- architecture context?
- license?
- production/reference/demo?

For design systems:

- official?
- versioned?
- accessibility documentation?
- engineering implementation available?
- tokens/primitives/patterns clearly separated?

For UI kits / design packs:

- source/license?
- design-only or coded?
- responsive evidence?
- interaction evidence?
- accessibility evidence?
- inspiration only?

For articles/community sources:

- author expertise?
- primary evidence?
- reproducible examples?
- dated technology assumptions?
- opinion vs measured result?
