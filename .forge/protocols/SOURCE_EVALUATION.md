# SOURCE EVALUATION PROTOCOL

## Universal questions

For every candidate source ask:

1. Who owns or publishes it?
2. What source type actually describes it?
3. What claim can this source legitimately support?
4. What authority weight applies to that claim and why?
5. What exact version, release, tag, commit, publication date, or platform context applies?
6. Is it current, version-bound, historical, superseded, or unknown?
7. What is the license/provenance state?
8. What may Lucien lawfully store: metadata, bounded excerpts, summaries/observations, or separately authorized vendoring?
9. Is the source independent of other compared sources, or merely repeating them?
10. What limitations prevent generalization?

## Standards and specifications

Ask:

- normative or explanatory?
- current version and status?
- official owner or standards body?
- exact normative scope?
- known implementation implications?
- superseded by a later normative document?

## Browser/platform documentation

Ask:

- first-party?
- browser/platform/version scope?
- normative platform rule or implementation note?
- compatibility data available?
- measured/runtime evidence separate from documentation?

## Framework/library documentation

Ask:

- first-party?
- exact version or release?
- stable/current versus legacy/deprecated page?
- documented contract versus tutorial convention?
- portability beyond this framework/library actually supported?

## Open-source repositories and reference implementations

Ask:

- exact repository and commit/tag?
- active maintenance status relevant to the claim?
- representative source path?
- real tests or runtime evidence?
- architecture context and constraints?
- license?
- production/reference/demo status?
- implementation-specific choice being overgeneralized?

## Design systems and component libraries

Ask:

- official owner?
- versioned?
- principles, tokens, primitives, components, and patterns clearly distinguished?
- accessibility documentation and tested behavior available?
- coded implementation available?
- product-specific convention versus general guidance?

## UI kits, design packs, templates, themes, and Figma resources

Ask:

- exact source and license?
- design-only or coded?
- responsive states actually demonstrated?
- interaction states actually demonstrated?
- accessibility evidence present?
- implementation evidence present?
- should authority be INSPIRATION_ONLY?

## Articles, case studies, postmortems, and community sources

Ask:

- author or team expertise identifiable?
- primary evidence linked?
- examples reproducible or inspectable?
- measured result versus opinion?
- technology assumptions dated?
- incentives or promotional framing?
- independently corroborated?
- anecdote being generalized beyond its scope?

## Evaluation result

Qualification records evidence strength and limits. It does not accept the source’s conclusions as Forge law.
